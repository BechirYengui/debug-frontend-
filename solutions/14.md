# Défi 14 : Mise en pause d'une campagne publicitaire

**Difficulté :** ★★☆ · **Famille :** le clic arrive, le code déraille.

## Cause

Rien ne casse, rien ne part : le clic fonctionne, mais l'envoi est **différé**, et le délai
est calculé avec la mauvaise unité. En tête de `public/c/14.js` (ligne 4) :

```js
var CFG = { confirmDelay: 900, unit: 's', maxRetries: 2 };
```

puis (lignes 31-33) :

```js
function delay() {
  return CFG.unit === 's' ? CFG.confirmDelay * 1000 : CFG.confirmDelay;
}
```

`confirmDelay` vaut 900 et a manifestement été pensé en millisecondes (un anti-rebond
de 0,9 s). Mais `unit` vaut `'s'`, donc `delay()` multiplie par 1000 :
**900 × 1000 = 900 000 ms, soit 15 minutes**. Le handler de clic (lignes 87-93) fait
ensuite tout ce qu'on attend de lui, sauf partir tout de suite :

```js
function schedule() {
  clearTimeout(pending);
  var ms = delay();                                   // <- 900000
  busy(true);
  log('mise en pause programmée, confirmation en cours…');
  pending = setTimeout(function () { send(); }, ms);  // <- dans 15 minutes
}
```

Le bouton passe en « mise en pause programmée… », le journal annonce une confirmation en
cours, et `send()` : dont le `fetch` est parfaitement correct : ne sera appelé que dans un
quart d'heure. Chaque nouveau clic fait `clearTimeout(pending)` et **repousse encore**
l'échéance. Si tu attends 15 minutes sans recliquer, la requête finit par partir : c'est
voulu, et c'est précisément ce qui rend ce bug pénible en production (« ça marche parfois »).

## Diagnostic pas à pas

1. **Console** : aucune erreur au clic. **Network** : aucune requête. Pourtant la page
   réagit (bouton grisé, ligne de journal). Le code s'exécute donc bien : il ne va
   simplement pas jusqu'au `fetch`. Quand rien ne casse et que rien ne part, cherche
   un **différé** : `setTimeout`, `requestAnimationFrame`, une promesse jamais résolue,
   un `await` sur un événement.
2. **Sources** → `14.js` → `Ctrl+F` `setTimeout` : une seule occurrence, ligne 92,
   dans `schedule()`. Le second argument est `ms`.
3. Pose un point d'arrêt sur cette ligne 92 (clic dans la gouttière). Autre chemin, sans
   lire le code : **Sources** → panneau *Event Listener Breakpoints* → *Mouse* → coche
   *click*, puis clique sur le bouton ; tu es en pause dans le premier handler, avance en
   pas à pas (`F10`) jusqu'au `setTimeout`.
4. En pause, survole `ms` (ou tape `ms` dans la Console) : **900000**. Survole `CFG` :
   `{confirmDelay: 900, unit: 's', maxRetries: 2}`. Remonte à `delay()` : la
   multiplication par 1000 quand `unit === 's'` explique tout.
5. Pour confirmer sans attendre : dans la Console, `ms / 60000` → `15`.

## Contournements

**A. Modifier la variable locale pendant la pause**
Point d'arrêt sur la ligne 92 (`pending = setTimeout(...)`), clic sur le bouton. Une fois
en pause, la Console évalue **dans le scope de la fonction arrêtée** :
```js
ms = 0
```
puis `F8` (reprendre). Le `setTimeout` est armé avec 0 ms, `send()` part immédiatement,
le journal affiche « envoi de la mise en pause » puis « réponse 200 ».

**B. Point d'arrêt conditionnel qui corrige au passage**
Clic droit sur la gouttière de la ligne 92 → *Add conditional breakpoint…* → condition :
```js
(ms = 0) && false
```
L'expression affecte `ms` puis vaut `false` : le débogueur ne s'arrête jamais, mais chaque
clic part désormais sans délai. Pratique quand on veut garder le flux normal de la page.

**C. Corriger la configuration pour toute la session**
En pause dans `schedule()` (ou n'importe où dans `14.js`), `CFG` est visible :
```js
CFG.unit = 'ms'
```
`F8`, puis reclique : `delay()` renvoie 900, l'envoi part après 0,9 s, comme prévu par
l'auteur. Retire ensuite le point d'arrêt. Attendre 15 minutes est aussi une option
« valide »… mais ce n'est pas celle qu'on attend d'un débogueur.

**D. Rejouer la requête depuis la Console**
```js
await fetch('/api/challenge/14/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '14', action: 'validate' })
}).then(r => r.json());
```

## Le réflexe à garder

**Rien ne casse + rien ne part = cherche un différé.** Un `setTimeout` avec une variable en
second argument mérite toujours un survol en pause : les erreurs d'unité (secondes vs
millisecondes, minutes vs secondes) ne déclenchent aucune exception, elles font juste
« attendre ». Et retiens que la Console, quand le débogueur est en pause, s'exécute dans le
scope de la ligne arrêtée : tu peux **lire et modifier** les variables locales (`ms = 0`),
pas seulement les globales. C'est l'outil le plus sous-utilisé de DevTools.
