# Défi 16 : Publication d'une grille tarifaire

**Difficulté :** ★★☆ · **Famille :** la requête part, mais elle ne convient pas.
Le code est dans `public/c/16.js`, lisible (non minifié). Défi **à jeton** : l'endpoint exige `X-Api-Token`.

## Cause

Le fragment HTML embarque un « handoff » SSO, un bloc JSON inerte dans le workspace :

```html
<script id="sso-handoff" type="application/json">
{"provider":"sso-corp","token":"ops_7c1e4b0a9d2f6e8c3b5a1f0d",
 "issuedAt":"2026-08-12T07:41:09Z","expiresAt":"2027-08-12T07:41:09Z", ...}
</script>
```

Au chargement, le script le recopie dans `localStorage` sous la clé `pricing.session`
si rien ne s'y trouve déjà :

```js
function seedFromHandoff() {
  if (readStore()) return;
  var node = byId('sso-handoff');
  ...
  writeStore(JSON.parse(node.textContent));     // <- jeton figé, expiration en 2027
  log('session restaurée depuis le handoff SSO');
}
```

Puis la logique de session est « cache d'abord » :

```js
function cached() {
  var c = readStore();
  return c && c.token && new Date(c.expiresAt).getTime() > Date.now() ? c : null;
}

function getSession() {
  var c = cached();
  if (c) { return Promise.resolve({ token: c.token, ..., source: 'cache local' }); }
  return fetch('/api/session', ...)      // <- jamais atteint tant que le cache est « valide »
```

Le jeton du handoff expire en août **2027** : `cached()` le considère valide, `/api/session`
n'est **jamais appelé**, et le clic envoie une requête par ailleurs impeccable (POST, JSON,
`challengeId`, `action`) avec l'en-tête `X-Api-Token: ops_7c1e4b0a9d2f6e8c3b5a1f0d`.
Ce jeton n'est pas celui de la session en cours : il a été émis pour une autre session, et le
serveur ne connaît que la sienne. Réponse **403** : `En-tête « X-Api-Token » présent mais sa valeur
ne correspond pas à la session en cours (jeton reçu se terminant par « …1f0d », attendu « …xxxx »).`

Le piège : la carte « Session applicative » affiche fièrement une session `active`, un jeton
masqué `ops_....1f0d` et une source `cache local`. Tout a l'air en ordre.

## Diagnostic pas à pas

1. **Network** : la requête `solve` part bien. Méthode `POST`, `Content-Type: application/json`,
   corps correct. Statut **403** (pas 401 : l'en-tête est là, c'est sa **valeur** qui est refusée).
2. Onglet **Headers** → *Request Headers* : `X-Api-Token: ops_7c1e4b0a9d2f6e8c3b5a1f0d`.
   Onglet **Response** : « présent mais sa valeur ne correspond pas à la session en cours », avec
   les quatre derniers caractères du jeton reçu et de celui attendu : ils diffèrent.
3. Filtre le Network sur `session` : **aucun** `GET /api/session` n'a été émis depuis le chargement.
   D'où sort ce jeton, alors ?
4. La carte Session dit « source : cache local » et « émis le 12 août 2026 ». Onglet
   **Application** → *Storage* → **Local Storage** → l'origine du dojo → clé `pricing.session` :
   ```json
   {"provider":"sso-corp","token":"ops_7c1e4b0a9d2f6e8c3b5a1f0d",
    "issuedAt":"2026-08-12T07:41:09Z","expiresAt":"2027-08-12T07:41:09Z",...}
   ```
   Le jeton se termine par `1f0d`, comme l'affichage masqué. Il vient de là.
5. Compare avec la vraie session, dans la **Console** :
   ```js
   await (await fetch('/api/session')).json()
   ```
   Le `token` renvoyé est différent, et ses quatre derniers caractères sont ceux que la réponse
   403 annonçait comme attendus. Le cache est périmé par rapport à la session courante, mais pas
   d'après sa propre date d'expiration.
6. **Sources** → `16.js` : `cached()` ne teste que `expiresAt`, `getSession()` ne rappelle
   `/api/session` que si `cached()` renvoie `null`, et `seedFromHandoff()` a rempli le cache
   depuis le bloc `<script id="sso-handoff">`.

## Contournements

**A. Purger la clé depuis l'onglet Application (le plus propre)**
Application → Local Storage → clic droit sur `pricing.session` → **Delete**. Puis clique
directement sur « Valider la commande », **sans recharger** : `cached()` renvoie `null`,
`getSession()` appelle `/api/session`, stocke le jeton frais et l'envoi part avec la bonne
valeur → **200**.
Pourquoi sans recharger ? Parce qu'au chargement `seedFromHandoff()` ne recopie le handoff
que si le stockage est vide, et après ta suppression, il l'est. Supprimer puis recharger
te ramène donc exactement au point de départ (le journal affiche à nouveau « session
restaurée depuis le handoff SSO »). Si tu as déjà rechargé, supprime la clé une nouvelle
fois et clique.

**B. La même chose depuis la Console**
```js
localStorage.removeItem('pricing.session');
document.getElementById('publish-grid').click();
```
Le clic déclenche `getSession()`, qui ne trouve plus de cache et négocie une session fraîche
avant d'envoyer. La carte Session n'est pas rafraîchie (elle ne l'est qu'au chargement),
mais le journal affiche « réponse 200 ».

**C. Périmer le cache au lieu de le supprimer**
Application → Local Storage → double-clic sur la valeur de `pricing.session` → remplace
`"expiresAt":"2027-08-12T07:41:09Z"` par une date passée, par ex. `"expiresAt":"2020-01-01T00:00:00Z"`,
valide avec Entrée, puis **recharge**. Cette fois recharger est la bonne idée : le stockage
n'est pas vide, donc le handoff n'est pas recopié ; `cached()` renvoie `null`, et
`getSession()` remplace l'entrée périmée par une session fraîche. La carte Session affiche
« session fraîche » et le bouton fonctionne.

**D. Rejouer la requête depuis la Console avec le jeton frais**
```js
const { token } = await (await fetch('/api/session')).json();
await fetch('/api/challenge/16/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'X-Api-Token': token },
  body: JSON.stringify({ challengeId: '16', action: 'validate' })
}).then(r => r.json());
```

**Après une remise à zéro du défi** : le bouton « reset » du tableau de bord purge la clé
`pricing.session`. Si tu remets le défi à zéro autrement (ou si tu changes de navigateur),
purge la clé à la main. Un cache dont la validité ne dépend que d'une date écrite par le client
ne se resynchronise jamais avec la session courante : c'est justement pour ça qu'un cache qui
« n'expire jamais » finit toujours par mentir.

## Le réflexe à garder

- **401** = le secret est **absent**. **403** = le secret est **présent mais refusé**.
  Un 403 sur une requête bien formée dit : « tu as une valeur, mais pas la bonne ».
- Quand la page a un jeton **sans avoir fait aucune requête d'authentification**, il vient
  d'un stockage : `localStorage`, `sessionStorage`, cookie, IndexedDB. L'onglet
  **Application** est le premier endroit à ouvrir.
- Une logique « cache d'abord » dont la validité ne dépend que d'une date écrite par le
  client ne se resynchronise jamais avec le serveur. Comparer la valeur cachée avec la valeur
  fraîche (`await (await fetch('/api/session')).json()`) tranche en dix secondes.
