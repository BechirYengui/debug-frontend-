# Défi 11 : Import d'un fichier CSV

**Difficulté :** ★★★ · **Famille :** la requête part, mais elle est invalide.
Le code est dans `public/c/11.js`, minifié sur une ligne.

## Cause

Le payload est correctement construit :

```js
function bld() {
  return {
    challengeId: "11",
    action: "validate",
    separator: S.sep,
    accepted: S.rows.length,
    rejected: S.bad.length,
    sample: S.rows.slice(0, 3)
  };
}
```

mais il est passé **tel quel** à `fetch` :

```js
function tx() {
  var p = bld();
  log("import soumis : " + p.accepted + " lignes");
  fetch("/api/challenge/11/solve", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: p                       // <- objet JS, pas de JSON.stringify
  })
  ...
}
```

`fetch` n'accepte comme corps qu'un `string`, `Blob`, `FormData`, `URLSearchParams`,
`ArrayBuffer` ou `ReadableStream`. Un objet ordinaire ne correspond à aucun de ces types :
la spec le convertit en chaîne via `String(value)`, ce qui donne littéralement
**`[object Object]`** : 15 octets.

Il n'y a **aucune erreur** : ni `fetch`, ni le navigateur, ni TypeScript (s'il y en avait) ne
protègent contre ça. Le `Content-Type: application/json` est bien présent et correct : c'est
le corps qui ne l'est pas. Le serveur essaie de parser `[object Object]`, échoue, et répond `400`.

## Diagnostic pas à pas

1. **Network** : la requête part, `POST`, statut **400**.
2. Onglet **Headers** : `Content-Type: application/json` : correct. Ce n'est pas le défi 10.
3. Onglet **Payload** (ou **Request**) : c'est ici que tout se joue.
   Chrome n'arrive pas à l'afficher comme du JSON ; clique sur **view source** :
   ```
   [object Object]
   ```
   `Content-Length: 15`. Quinze octets pour un payload censé contenir un échantillon de lignes :
   l'écart est flagrant.
4. Onglet **Response** :
   `Corps recu illisible en JSON (15 octets). Ce qui est arrive commence par : « [object Object] ».`
   Le terminal `npm start` affiche la même chaîne en `body brut`.
5. `[object Object]` est une **signature** : c'est le résultat de `String(obj)`. Dès que tu la
   vois passer sur le réseau, la cause est toujours la même : une valeur non sérialisée.
6. **Sources** → `11.js` → **Pretty print `{}`** → cherche `fetch`.
   Pose un point d'arrêt sur la ligne du `fetch`, clique sur le bouton, puis en Console
   pendant la pause :
   ```js
   typeof p          // "object"
   String(p)         // "[object Object]"
   JSON.stringify(p) // '{"challengeId":"11","action":"validate",...}'  <- ce qu'il fallait envoyer
   ```

## Contournements

**A. Rejouer avec un corps sérialisé (Console)**
```js
await fetch('/api/challenge/11/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '11', action: 'validate' })
}).then(r => r.json());
```

**B. Sérialiser à chaud sur le point d'arrêt**
Point d'arrêt sur la ligne du `fetch` (après pretty-print), clic sur le bouton, puis dans la
Console pendant la pause :
```js
p = JSON.stringify(p);   // `p` devient une chaine dans le scope courant
```
Reprends (`F8`) : la requête part avec le bon corps.

**C. Intercepter `fetch` et sérialiser tout objet**
```js
const orig = window.fetch;
window.fetch = (u, i = {}) => orig(u,
  (i.body && typeof i.body === 'object' && !(i.body instanceof FormData))
    ? { ...i, body: JSON.stringify(i.body) } : i);
document.getElementById('run-import').click();
```
Cette version-là envoie le vrai payload de la page (avec `separator`, `accepted`, `sample`…),
pas un payload minimal reconstruit à la main.

## Le réflexe à garder

**`[object Object]` sur le réseau = `JSON.stringify` oublié.** Point.
L'onglet **Payload** avec *view source* est le seul endroit qui montre les octets réellement
transmis : la vue « jolie » de DevTools peut te faire croire à un objet là où il n'y a qu'une
chaîne. Et `fetch` ne sérialise jamais pour toi : contrairement à axios, qui le fait
automatiquement. C'est exactement l'erreur qu'on commet en migrant d'axios vers `fetch`.
