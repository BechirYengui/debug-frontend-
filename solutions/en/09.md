# Challenge 09: Firmware update

**Difficulty:** ★★☆ · **Family:** the request goes out, but it is not what the server expects.

## Cause

The page goes through a home-made mini HTTP client:

```js
var api = {
  request: function (url, opts) {
    opts = opts || {};
    var method = (opts.method || 'GET').toUpperCase();   // <- default GET
    var init = { method: method, headers: {} };
    ...
    if (opts.json !== undefined && method !== 'GET' && method !== 'HEAD') {
      init.headers['Content-Type'] = 'application/json';
      init.body = JSON.stringify(opts.json);
    }
    return fetch(url, init) ...
  }
};
```

and the caller forgets to specify the verb:

```js
api.request('/api/challenge/09/solve', {
  headers: { Accept: 'application/json' },
  json: { challengeId: '09', action: 'validate', ... }   // <- no `method`
});
```

The helper falls back to its `GET` default. And since a `GET` cannot carry a body
(`fetch` would throw `TypeError: Request with GET/HEAD method cannot have body`), the helper
takes care **not to attach the body nor the Content-Type** in that case. So the request goes out
as a `GET`, with no body, no media type: the server answers `405` and the terminal log
shows `body brut : (vide)` (raw body: empty).

The trap: the helper is correct, the caller is incomplete, and the chosen default hides the omission
instead of flagging it.

## Step-by-step diagnosis

1. **Network**: on click, a `solve` line appears: that is already good news,
   the request goes out. It is red, status **405**.
2. **Method** column: `GET`. The Objective box requires `POST`. Diagnosis complete.
   (If the Method column is not shown: right-click the table header → check *Method*.)
3. Open the request → **Headers**:
   - *Request Method: GET*
   - no `Content-Type`
   - **Payload** tab absent: there is no body.
4. **Response** tab: the server says exactly what it received:
   `Verbe recu : GET. Cet endpoint ne traite pas ce verbe.` (Verb received: GET. This endpoint does not handle this verb.)
5. The `npm start` terminal confirms the same thing on the server side.
6. **Sources** → `09.js` → search for `fetch`. You trace back to `api.request` and its
   `opts.method || 'GET'`, then to the call that passes no `method`.

## Workarounds

**A. Replay the request correctly (Console)**
```js
await fetch('/api/challenge/09/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '09', action: 'validate' })
}).then(r => r.json());
```

**B. Start from the existing request (Network)**
Right-click the `solve` line → **Copy** → *Copy as fetch*. Paste into the Console and fix
the three points: `method: 'POST'`, add `Content-Type`, add the `body`. This is the fastest
move in an interview: you start from what exists, you show exactly what you change.

**C. Hot-fix the helper (Console)**
The helper lives in a closure, but you can intercept upstream:
```js
const orig = window.fetch;
window.fetch = (url, init = {}) => {
  if (String(url).includes('/solve')) {
    init = { ...init, method: 'POST',
             headers: { ...(init.headers || {}), 'Content-Type': 'application/json' },
             body: JSON.stringify({ challengeId: '09', action: 'validate' }) };
  }
  return orig(url, init);
};
document.getElementById('push-firmware').click();
```

## The reflex to keep

As soon as the request **goes out**, the debate shifts: it is no longer "why does nothing happen"
but "what exactly am I sending". Network → Method, Status, Headers, Payload, in
that order. An HTTP helper with a default verb is a nest of bugs: the code compiles, goes out,
and fails only on the server side. *Copy as fetch* is your best starting point to
replay and fix.
