# Challenge 10: Internal transfer

**Difficulty:** ★★★ · **Family:** the request goes out, but it's not the right one.
The code lives in `public/c/10.js`, minified on a single line.

## Cause

The application's headers are built once and for all, at startup:

```js
E.hdr = {
  "Accept": "application/json",
  "X-Client": "backoffice-web/4.2",
  "X-Request-Id": "rq-" + Math.random().toString(36).slice(2, 10)
};
```

and reused as-is when sending:

```js
fetch("/api/challenge/10/solve", {
  method: "POST",
  headers: E.hdr,                 // <- no Content-Type
  body: JSON.stringify(p)         // <- the body itself is valid JSON
})
```

`Content-Type` is missing. When `body` is a string and no `Content-Type` is provided,
`fetch` does not fail: it **makes one up**. The specification then mandates
`text/plain;charset=UTF-8`. So the server receives perfectly well-formed JSON, announced as
plain text, and rejects it with a `415`.

This is the most treacherous bug in the series: the body is right, the method is right, the URL
is right. Only the label is wrong, and **nobody in the code ever wrote `text/plain`**.

## Step-by-step diagnosis

1. **Network**: the request goes out, `POST`, status **415**. The method is correct: the problem
   lies somewhere other than the verb.
2. **Payload** tab: the body is `{"challengeId":"10","action":"validate",...}`.
   It is valid. So it is not the body either.
3. **Headers** tab → **Request Headers** section:
   ```
   Content-Type: text/plain;charset=UTF-8
   X-Client: backoffice-web/4.2
   X-Request-Id: rq-...
   ```
   Search for `text/plain` in the source code: **nowhere to be found**. That is the sign that the
   browser added it on its own, for lack of an explicit header.
   (If Chrome shows "Provisional headers are shown", click *Raw* to see the headers that were
   actually sent.)
4. **Response** tab: `Content-Type received: "text/plain;charset=UTF-8". That is not the media type this endpoint accepts.`
5. The "Server log" panel shows the same thing, with the raw body next to it: the comparison
   "what I think I am sending / what actually arrives" is immediate.
6. **Sources** → `10.js` → **Pretty print `{}`** → search for `headers`. The `E.hdr` object only
   contains three keys, none of which is `Content-Type`.
   Live check, on a breakpoint set on the `fetch` line:
   `Object.keys(E.hdr)` → `["Accept","X-Client","X-Request-Id"]`.

## Workarounds

**A. Replay with the right header (Console)**
```js
await fetch('/api/challenge/10/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '10', action: 'validate' })
}).then(r => r.json());
```

**B. Copy as fetch + one line**
Network → right-click the request → *Copy as fetch*. Paste it in the Console and add
`"Content-Type": "application/json"` inside `headers`. Nothing else to change: the copied body
is already correct. This is the most telling demonstration that the only defect is the label.

**C. Patch the headers object live (breakpoint)**
Set a breakpoint on the `fetch` line (after pretty-printing), click the button,
then in the Console while paused:
```js
E.hdr['Content-Type'] = 'application/json';
```
Resume (`F8`). Since the headers object is shared, every subsequent send is correct too.

**D. Intercept `fetch`**
```js
const orig = window.fetch;
window.fetch = (u, i = {}) => orig(u, i.body
  ? { ...i, headers: { ...(i.headers || {}), 'Content-Type': 'application/json' } } : i);
document.getElementById('execute-transfer').click();
```

## The reflex to keep

A `415` never says "your JSON is wrong": it says "your label is wrong".
When a header shows up in Network **without existing in the code**, the browser put it there:
`Content-Type`, `Content-Length`, `Origin`, `Referer`, `Sec-Fetch-*`.
Remember the rule: `fetch` + string `body` + no `Content-Type` = `text/plain;charset=UTF-8`.
(With a `FormData` or a `URLSearchParams`, it would be `multipart/form-data` or
`application/x-www-form-urlencoded`: never JSON.)
