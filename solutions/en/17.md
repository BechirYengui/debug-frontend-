# Challenge 17: Exporting accounting entries

**Difficulty:** ★★★ · **Family:** the request goes out, but it's not the right one.
The code lives in `public/c/17.js` and `public/c/17-guard.js`, minified on a single line.

## Cause

The page's script is beyond reproach. On click, `tx()` sends:

```js
fetch("/api/challenge/17/solve", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ challengeId: "17", action: "validate", period: S.period, format: S.format, recipient: S.recipient })
})
.then(function (r) { return r.json().then(function (j) { return { s: r.status, j: j }; }); })
.then(function (x) {
  log("réponse " + x.s + " : " + (x.j.message || x.j.error));
  if (x.s === 202) { E.chip.className = "chip chip-warn"; E.chip.textContent = "en attente de revue"; }
})
```

The problem lies elsewhere: in the fragment's `<head>`, **before** this script, a second
file is loaded without `defer`:

```html
<link rel="stylesheet" href="/c/17.css">
<script src="/c/17-guard.js"></script>
```

`17-guard.js` ("privacy guard") **replaces `window.fetch`**:

```js
(function (w) {
  var nf = w.fetch;                                   // <- the real fetch, kept in a closure
  var ALLOW = [/\/api\/session\b/, /\/api\/telemetry\b/, /\/_dojo\//];
  function held(u, i) {
    var m = ((i && i.method) || "GET").toUpperCase();
    if (m === "GET" || m === "HEAD") return false;    // reads go through
    if (!/\/api\//.test(u)) return false;
    for (var k = 0; k < ALLOW.length; k++) { if (ALLOW[k].test(u)) return false; }
    return true;                                      // any unlisted POST /api/... is held
  }
  function quarantine(u, i) {
    ...
    console.debug("[privacy-guard] requête retenue pour revue : POST " + u + " (q-1)");
    return Promise.resolve(new Response(body, { status: 202, headers: { "Content-Type": "application/json" } }));
  }
  w.fetch = function (u, i) {
    var s = str(u);
    if (held(s, i)) return quarantine(s, i);          // <- answers 202 WITHOUT touching the network
    return nf.apply(w, arguments);
  };
})(window);
```

`POST /api/challenge/17/solve` is not on the allow list: the wrapper fabricates a
**202** `Response` out of thin air and returns it. **Not a single byte leaves.** The page, in good
faith, logs "réponse 202 : Requête mise en quarantaine…" (response 202: request quarantined) and
switches the chip to "en attente de revue" (pending review). The server, for its part, never
received anything.

## Step-by-step diagnosis

1. **The three mirrors disagree.** The page's log claims "réponse 202".
   The page's "Server log" panel stays empty (and, locally, the server terminal shows
   nothing). And above all: in **Network**, there is **no `solve` request**, even
   without a filter, even with *Preserve log* ticked. A 202 without a network request does not
   exist. So this 202 did not come from the network: someone fabricated it inside the page.
2. **Console** → type `fetch` and press Enter. A native `fetch` displays as `ƒ fetch() { [native code] }`.
   Here you get `ƒ (u, i){var s=str(u);if(held(s,i)){return quarantine(s,i);}…}`:
   `window.fetch` has been **replaced**. `fetch.toString()` gives the same verdict in plain text.
3. Click `ƒ (u, i)…` in the Console: DevTools opens **Sources** on the definition,
   in `17-guard.js`. Click **`{}`** (Pretty print). You see `nf = w.fetch`, the
   `ALLOW` list, `held()`, `quarantine()` and the `new Response(..., {status: 202})`.
4. Confirmation from the hidden log: in the Console, set the level to **Verbose**
   (*Default levels* menu → tick *Verbose*), click the button again: the line
   `[privacy-guard] requête retenue pour revue : POST /api/challenge/17/solve (q-2)` appears.
   It had been there from the start, filtered out by the default level.
5. Where is this script loaded? **Network** → filter `JS` → `17-guard.js`, **Initiator** column:
   the document itself (`17`), that is, a `<script>` tag in the `<head>`, loaded before
   `17.js`. **Elements** → `<head>`: the tag is visible.
6. To see the real `fetch`: breakpoint inside the wrapper (Sources, `17-guard.js`
   pretty-printed, line `var s = str(u)`), click the button, and at the pause the
   **Scope** panel → *Closure* shows `nf: ƒ fetch() { [native code] }`.

## Workarounds

**A. Block the guard script (the cleanest)**
Network → right-click `17-guard.js` → **Block request URL** → reload (`F5`).
The script no longer loads, `window.fetch` stays native, clicking "Valider la commande" (Submit)
sends the real request → **200**. (Same result from Sources → *Network request blocking*
tab.) Do not forget to unblock afterwards.

**B. Restore the native fetch from the pause**
Set a breakpoint inside the wrapper (`17-guard.js` pretty-printed, line `var s = str(u)`),
click the button. At the pause, in the Console (which evaluates in the closure's scope):
```js
window.fetch = nf
```
Then `F8`. This particular call is still intercepted (it had already entered the wrapper),
but **the next click** goes through the native fetch → 200.

**C. Recover a native fetch via an iframe (no breakpoint)**
```js
const f = document.createElement('iframe');
document.body.appendChild(f);
window.fetch = f.contentWindow.fetch.bind(window);
document.getElementById('send-export').click();
```
The `fetch` of a brand-new window has not been wrapped. Bound to `window`, it does the job
of the page's native fetch; the button then works normally.

**D. Bypass `fetch` with `XMLHttpRequest` (Console)**
`XMLHttpRequest` is not wrapped. Full request:
```js
const x = new XMLHttpRequest();
x.open('POST', '/api/challenge/17/solve');
x.setRequestHeader('Content-Type', 'application/json');
x.onload = () => console.log(x.status, x.responseText);
x.send(JSON.stringify({ challengeId: '17', action: 'validate' }));
```

**E. Replay the request from the Console, but not this page's Console**
The usual replay:
```js
await fetch('/api/challenge/17/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '17', action: 'validate' })
}).then(r => r.json());
```
**fails** if you type it in the challenge page's Console: the Console uses the page's
`fetch`, hence the wrapper, and you get a fabricated 202: the server still sees
nothing. Run exactly the same code from the Console of **another tab** on the same
origin (the dashboard, for example, which does not load `17-guard.js`), or from a
terminal:
```sh
curl -s -X POST http://localhost:3000/api/challenge/17/solve \
  -H 'Content-Type: application/json' \
  -b 'dojo_session=<cookie value, Application → Cookies tab>' \
  -d '{"challengeId":"17","action":"validate"}'
```
(adjust the port to the one shown at server startup). The cookie is essential: without it, the
server does answer 200, but `Command accepted, but not credited: no player session (send the
request from your signed-in browser).` The challenge passes as soon as the server recognizes your
account: validation is server-side, no matter which tab the request leaves from.

## The reflex to keep

When **the application's log and the Network tab contradict each other, it is the page that is
lying**, never Network: DevTools observes the browser's network layer, beneath anything
JavaScript can rewrite. A "success" with no row in Network is a fabricated success.
First move: `fetch` in the Console: if you do not read `[native code]`, a third-party
script (analytics, "privacy guard", error SDK, polyfill) has wedged itself in, and the
Console is no longer any use for replaying anything until you have neutralized it.
Second move: **Verbose** level, where these scripts often leave their confessions.
