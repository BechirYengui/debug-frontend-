# Challenge 15: Signing a purchase order

**Difficulty:** ★★☆ · **Family:** the request goes out, but it is not what the server expects.

## Cause

The code builds the API address itself, and it picks a **different origin** from the
page's. At the top of `public/c/15.js` (lines 4-9):

```js
var GATEWAY = {
  primary: location.origin,
  replica: location.protocol + '//' + location.hostname + ':' +
    (parseInt(location.port || (location.protocol === 'https:' ? '443' : '80'), 10) + 1),
  prefer: 'replica'                                   // <- the "replica" is preferred
};
```

then (lines 31-33 and 96):

```js
function apiBase() {
  return GATEWAY.prefer === 'replica' ? GATEWAY.replica : GATEWAY.primary;
}
...
fetch(apiBase() + '/api/challenge/15/solve', { method: 'POST', ... })
```

If the page is served on `http://localhost:3000`, `GATEWAY.replica` is
`http://localhost:3001`: same scheme, same host, **different port**, hence a different
origin. The server does listen on that neighboring port, with the same application, but without
any CORS header.

A `POST` with `Content-Type: application/json` to another origin is not a
"simple request": the browser first sends a **preflight** `OPTIONS` to ask for
permission. The server answers `405` without `Access-Control-Allow-Origin`; the browser
concludes that the origin `http://localhost:3000` is not allowed, **blocks**, and never
issues the `POST`. The `fetch` is rejected with `TypeError: Failed to fetch`, which the page's
log honestly displays: "échec réseau : Failed to fetch" (network failure). Verb, header,
body: everything is correct: it is the **address** that is wrong.

## Step-by-step diagnosis

1. **Console**, click *Valider la commande* (Submit): a long red message that has to be read
   in full:
   `Access to fetch at 'http://localhost:3001/api/challenge/15/solve' from origin
   'http://localhost:3000' has been blocked by CORS policy: Response to preflight request
   doesn't pass access control check: No 'Access-Control-Allow-Origin' header is present on
   the requested resource.`
   It already contains everything: the target URL (port **3001**), the page's origin (port
   **3000**), the word *preflight* and the missing header.
2. **Network**: the `solve` row is red, Status column: **CORS error**. Check the
   filter at the top of the panel: on *Fetch/XHR*, you only see the blocked request; switch to
   *All* (or *Other*) to see the **second** `solve` row appear, Type column
   `preflight`, method `OPTIONS`, status 405. Open it → **Headers**: the request carries
   `Origin: http://localhost:3000` and `Access-Control-Request-Method: POST`; the response has
   no `Access-Control-*` header at all.
3. **Server terminal** (`npm start`): it did receive something: an
   `OPTIONS /api/challenge/15/solve` with the `origin` header, and nothing else. You wrote
   no `OPTIONS`: the browser issued it on your behalf. The `POST`, for its part,
   never arrived.
4. **Sources** → `15.js` → `Ctrl+F` `fetch`: the URL is `apiBase() + '/api/...'`. Go back up to
   `apiBase()`, then to `GATEWAY`: `prefer: 'replica'` and the `location.port + 1` computation.
   The page's log said so from the moment it loaded: "passerelle sélectionnée : réplica"
   (selected gateway: replica).
5. Confirm the expected origin: in the Console, `location.origin` →
   `"http://localhost:3000"`. **That** is where the request must go.

## Workarounds

**A. Replay the request from the Console, with a relative URL**
A relative URL is resolved against the page's origin: no more CORS, no more preflight.
```js
await fetch('/api/challenge/15/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '15', action: 'validate' })
}).then(r => r.json());
```

**B. Switch the gateway during a debugger pause**
Breakpoint on line 96 (`fetch(apiBase() + ...)`) in `sign()`, click the button.
While paused, `GATEWAY` is in the closure's scope:
```js
GATEWAY.prefer = 'primary'
```
`F8`: `apiBase()` now returns `location.origin`, the `POST` goes out to the right origin,
the log shows "réponse 200" (response 200). Remove the breakpoint; the setting holds for the
whole session.

**C. Start from the blocked request (Network → Copy as fetch)**
Right-click the `solve` row (the one in *CORS error*) → **Copy** → *Copy as fetch*. Paste
it in the Console, and replace `"http://localhost:3001/api/challenge/15/solve"` with
`"/api/challenge/15/solve"`. Everything else (method, headers, body) is already correct:
you show exactly what you change, and nothing else.

**D. Fix the served file (Sources → Overrides)**
**Sources** → *Overrides* tab → *Select folder for overrides*, grant access. Open
`15.js`, replace `prefer: 'replica'` with `prefer: 'primary'`, `Ctrl+S`. The file is
now served from your disk, even after a reload: this is the clean way to
test a front-end fix without redeploying.

## The reflex to keep

An origin is **scheme + host + port**, all three together: `localhost:3000` and
`localhost:3001` are two origins foreign to each other. An `OPTIONS` you did not
write in your code is a **preflight**: the browser asks for permission before
sending your real request, and if the answer does not grant it, that real request never
exists (neither in Network strictly speaking, nor on the server side). Faced with "blocked by
CORS policy", read the message to the end: it names the origin and the target, then ask the
only useful question: *why is the client targeting another origin?* The client-side fix is
almost always the same: **a relative URL, hence the same origin.**
