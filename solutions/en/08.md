# Challenge 08: Closing a ticket

**Difficulty:** ★★★ · **Family:** the click arrives, but the code goes off the rails.
The code lives in `public/c/08.js`, minified on a single line.

## Cause

The button's handler:

```js
E.close.addEventListener("click", function () {
  busy(true);
  try {
    var p = payload();
    tx(p);
  } catch (err) {}      // <- empty block
  busy(false);
});
```

and the payload builder:

```js
function payload() {
  return {
    challengeId: "08",
    action: "validate",
    ticket: T.id,
    resolution: st.res,
    closedBy: ss.profile.handle,   // <- ss.profile is undefined
    notify: st.notify
  };
}
```

`ss.profile` is only assigned conditionally, higher up:

```js
var ss = { id: "sess-7712", roles: ["agent", "reader"], since: Date.now() };
if (ss.roles.indexOf("supervisor") !== -1) { ss.profile = { handle: "n2-lead", scope: "all" }; }
```

The current session has the roles `agent` and `reader`, never `supervisor`: `ss.profile` stays
`undefined`. `payload()` throws `TypeError: Cannot read properties of undefined (reading 'handle')`.
The empty `catch (err) {}` absorbs it: no log, no trace, the Console stays spotless.
`tx(p)`, which contains a perfectly correct `fetch`, is never reached.

The button, however, **visibly responds**: `busy(true)` then `busy(false)` make the
label flash to "envoi..." (sending...). You believe something is happening. That is the trap.

## Step-by-step diagnosis

1. **Network**: nothing on click. **Console**: nothing either. But the button reacts
   visually → the handler does run, it stops partway through.
2. **Sources** → right-hand panel → check **Pause on uncaught exceptions**, then the
   sub-checkbox **Pause on caught exceptions**. That is the decisive move of this challenge: by default,
   DevTools ignores caught exceptions, hence the ones an empty `catch` makes disappear.
3. Click. The debugger stops on `closedBy: ss.profile.handle`, with the tooltip
   `TypeError: Cannot read properties of undefined (reading 'handle')`.
   Hover `ss`: `{id: "sess-7712", roles: ["agent","reader"], since: ...}`: no `profile`.
4. Walk up the **Call Stack**: `payload` ← the `click` handler. Look at the surrounding code:
   `try { ... } catch (err) {}`. The block is empty, the error is lost.
5. Alternative approach, without the checkboxes: Sources → **Event Listener Breakpoints** →
   *Mouse* → `click`, click, then step with `F10` / `F11`. You see execution enter
   `payload()` and come straight back out at `busy(false)`, skipping `tx(p)`.
6. The code is on one line: click **`{}`** (Pretty print) at the bottom of the Sources panel
   before setting your breakpoints, otherwise the whole file is a single line 1.

## Workarounds

**A. Repair the missing data, then click (Console)**
`ss` lives in a closure, but the breakpoint gives you access to its scope. Set a
breakpoint in `payload()`, click, and in the Console (in the paused context):
```js
ss.profile = { handle: 'n2-lead' };
```
Resume execution (`F8`), then click the button again: `payload()` no longer throws, `tx()`
goes out, the server answers 200.

**B. Conditional breakpoint / logpoint**
Right-click the `closedBy: ...` line → *Add conditional breakpoint* → condition:
```js
(ss.profile = ss.profile || {handle: 'n2-lead'}) && false
```
The condition assigns the value then returns `false`: the debugger never stops and the
bug is fixed on the fly. (Same principle with a *Logpoint*.)

**C. Replay the request**
```js
await fetch('/api/challenge/08/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '08', action: 'validate' })
}).then(r => r.json());
```

## The reflex to keep

A handler that **reacts visually** but sends nothing = it stops in the middle.
**Pause on caught exceptions** is the checkbox that reveals everything an empty `catch {}` hides;
most developers never check it. And on minified code, **Pretty print (`{}`) before
anything else**: without it, breakpoints and stepping are unusable.
