# Challenge 11: Importing a CSV file

**Difficulty:** ★★★ · **Family:** the request goes out, but it's not the right one.
The code lives in `public/c/11.js`, minified on a single line.

## Cause

The payload is built correctly:

```js
function bld() {
  return {
    challengeId: "11",
    action: "validate",
    separator: S.sep,
    accepted: S.rows.length,
    rejected: S.bad.length,
    sample: S.rows.slice(0, 3)
  };
}
```

but it is handed **as-is** to `fetch`:

```js
function tx() {
  var p = bld();
  log("import soumis : " + p.accepted + " lignes");
  fetch("/api/challenge/11/solve", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: p                       // <- a JS object, no JSON.stringify
  })
  ...
}
```

`fetch` only accepts a `string`, `Blob`, `FormData`, `URLSearchParams`,
`ArrayBuffer` or `ReadableStream` as a body. A plain object matches none of these types:
the spec converts it to a string via `String(value)`, which yields literally
**`[object Object]`**: 15 bytes.

There is **no error whatsoever**: neither `fetch`, nor the browser, nor TypeScript (if there were
any) protects you from this. The `Content-Type: application/json` is present and correct: it is
the body that is not. The server tries to parse `[object Object]`, fails, and answers `400`.

## Step-by-step diagnosis

1. **Network**: the request goes out, `POST`, status **400**.
2. **Headers** tab: `Content-Type: application/json`: correct. This is not challenge 10.
3. **Payload** tab (or **Request**): this is where it all plays out.
   Chrome cannot display it as JSON; click **view source**:
   ```
   [object Object]
   ```
   `Content-Length: 15`. Fifteen bytes for a payload supposed to contain a sample of rows:
   the gap is glaring.
4. **Response** tab:
   `Received body is not readable as JSON (15 bytes). What arrived starts with: "[object Object]".`
   The "Server log" panel shows the same string as the received body (15 bytes).
5. `[object Object]` is a **signature**: it is the result of `String(obj)`. As soon as you see it
   go over the wire, the cause is always the same: an unserialized value.
6. **Sources** → `11.js` → **Pretty print `{}`** → search for `fetch`.
   Set a breakpoint on the `fetch` line, click the button, then in the Console
   while paused:
   ```js
   typeof p          // "object"
   String(p)         // "[object Object]"
   JSON.stringify(p) // '{"challengeId":"11","action":"validate",...}'  <- what should have been sent
   ```

## Workarounds

**A. Replay with a serialized body (Console)**
```js
await fetch('/api/challenge/11/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '11', action: 'validate' })
}).then(r => r.json());
```

**B. Serialize live on the breakpoint**
Breakpoint on the `fetch` line (after pretty-printing), click the button, then in the
Console while paused:
```js
p = JSON.stringify(p);   // `p` becomes a string in the current scope
```
Resume (`F8`): the request goes out with the right body.

**C. Intercept `fetch` and serialize any object**
```js
const orig = window.fetch;
window.fetch = (u, i = {}) => orig(u,
  (i.body && typeof i.body === 'object' && !(i.body instanceof FormData))
    ? { ...i, body: JSON.stringify(i.body) } : i);
document.getElementById('run-import').click();
```
This version sends the page's real payload (with `separator`, `accepted`, `sample`, and so on),
not a minimal payload rebuilt by hand.

## The reflex to keep

**`[object Object]` on the wire = forgotten `JSON.stringify`.** Period.
The **Payload** tab with *view source* is the only place that shows the bytes actually
transmitted: the "pretty" view in DevTools can make you believe there is an object where there is
only a string. And `fetch` never serializes for you: unlike axios, which does it
automatically. This is exactly the mistake people make when migrating from axios to `fetch`.
