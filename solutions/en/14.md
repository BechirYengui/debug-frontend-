# Challenge 14: Pausing an advertising campaign

**Difficulty:** ★★☆ · **Family:** the click arrives, but the code goes off the rails.

## Cause

Nothing breaks, nothing goes out: the click works, but the send is **deferred**, and the delay
is computed with the wrong unit. At the top of `public/c/14.js` (line 4):

```js
var CFG = { confirmDelay: 900, unit: 's', maxRetries: 2 };
```

then (lines 31-33):

```js
function delay() {
  return CFG.unit === 's' ? CFG.confirmDelay * 1000 : CFG.confirmDelay;
}
```

`confirmDelay` is 900 and was obviously meant in milliseconds (a 0.9 s
debounce). But `unit` is `'s'`, so `delay()` multiplies by 1000:
**900 × 1000 = 900,000 ms, that is 15 minutes**. The click handler (lines 87-93) then
does everything expected of it, except leaving right away:

```js
function schedule() {
  clearTimeout(pending);
  var ms = delay();                                   // <- 900000
  busy(true);
  log('mise en pause programmée, confirmation en cours…');
  pending = setTimeout(function () { send(); }, ms);  // <- in 15 minutes
}
```

The button switches to "mise en pause programmée…" (pause scheduled), the log announces a
confirmation in progress, and `send()` (whose `fetch` is perfectly correct) will only be called
a quarter of an hour later. Every new click runs `clearTimeout(pending)` and **pushes the
deadline back again**. If you wait 15 minutes without clicking again, the request eventually
goes out: that is intended, and it is precisely what makes this bug painful in production ("it
works sometimes").

## Step-by-step diagnosis

1. **Console**: no error on click. **Network**: no request. Yet the page
   reacts (greyed-out button, log line). So the code does run: it simply does not
   make it to the `fetch`. When nothing breaks and nothing goes out, look for
   a **deferral**: `setTimeout`, `requestAnimationFrame`, a promise that never resolves,
   an `await` on an event.
2. **Sources** → `14.js` → `Ctrl+F` `setTimeout`: a single occurrence, line 92,
   in `schedule()`. The second argument is `ms`.
3. Set a breakpoint on that line 92 (click in the gutter). Another route, without
   reading the code: **Sources** → *Event Listener Breakpoints* panel → *Mouse* → tick
   *click*, then click the button; you are paused in the first handler, step
   forward (`F10`) until the `setTimeout`.
4. While paused, hover over `ms` (or type `ms` in the Console): **900000**. Hover over `CFG`:
   `{confirmDelay: 900, unit: 's', maxRetries: 2}`. Go back up to `delay()`: the
   multiplication by 1000 when `unit === 's'` explains everything.
5. To confirm without waiting: in the Console, `ms / 60000` → `15`.

## Workarounds

**A. Modify the local variable while paused**
Breakpoint on line 92 (`pending = setTimeout(...)`), click the button. Once
paused, the Console evaluates **in the scope of the stopped function**:
```js
ms = 0
```
then `F8` (resume). The `setTimeout` is armed with 0 ms, `send()` fires immediately,
the log shows "envoi de la mise en pause" (sending the pause) then "réponse 200".

**B. Conditional breakpoint that fixes things on the way through**
Right-click the gutter on line 92 → *Add conditional breakpoint…* → condition:
```js
(ms = 0) && false
```
The expression assigns `ms` then evaluates to `false`: the debugger never stops, but every
click now goes out without delay. Handy when you want to keep the page's normal flow.

**C. Fix the configuration for the whole session**
Paused in `schedule()` (or anywhere in `14.js`), `CFG` is visible:
```js
CFG.unit = 'ms'
```
`F8`, then click again: `delay()` returns 900, the send goes out after 0.9 s, as the
author intended. Then remove the breakpoint. Waiting 15 minutes is also a "valid"
option… but it is not the one expected of a debugger.

**D. Replay the request from the Console**
```js
await fetch('/api/challenge/14/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '14', action: 'validate' })
}).then(r => r.json());
```

## The reflex to keep

**Nothing breaks + nothing goes out = look for a deferral.** A `setTimeout` with a variable as
its second argument always deserves a hover while paused: unit errors (seconds vs
milliseconds, minutes vs seconds) throw no exception, they just make things
"wait". And remember that the Console, when the debugger is paused, runs in the
scope of the stopped line: you can **read and modify** local variables (`ms = 0`),
not just globals. It is the most underused tool in DevTools.
