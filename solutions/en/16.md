# Challenge 16: Publishing a price list

**Difficulty:** ★★☆ · **Family:** the request goes out, but it's not the right one.
The code lives in `public/c/16.js`, readable (not minified). **Token-based** challenge: the endpoint requires `X-Api-Token`.

## Cause

The HTML fragment embeds an SSO "handoff", an inert JSON block in the workspace:

```html
<script id="sso-handoff" type="application/json">
{"provider":"sso-corp","token":"ops_7c1e4b0a9d2f6e8c3b5a1f0d",
 "issuedAt":"2026-08-12T07:41:09Z","expiresAt":"2027-08-12T07:41:09Z", ...}
</script>
```

On load, the script copies it into `localStorage` under the key `pricing.session`
if nothing is there yet:

```js
function seedFromHandoff() {
  if (readStore()) return;
  var node = byId('sso-handoff');
  ...
  writeStore(JSON.parse(node.textContent));     // <- frozen token, expiring in 2027
  log('session restaurée depuis le handoff SSO');
}
```

Then the session logic is "cache first":

```js
function cached() {
  var c = readStore();
  return c && c.token && new Date(c.expiresAt).getTime() > Date.now() ? c : null;
}

function getSession() {
  var c = cached();
  if (c) { return Promise.resolve({ token: c.token, ..., source: 'cache local' }); }
  return fetch('/api/session', ...)      // <- never reached as long as the cache is "valid"
```

The handoff token expires in August **2027**: `cached()` considers it valid, `/api/session`
is **never called**, and the click sends an otherwise impeccable request (POST, JSON,
`challengeId`, `action`) with the header `X-Api-Token: ops_7c1e4b0a9d2f6e8c3b5a1f0d`.
That token is not the current session's: it was issued for another session, and the server only
knows its own. Answer **403**: `Header "X-Api-Token" is present but its value does not match the
current session (token received ends with "…1f0d", expected "…xxxx").`

The trap: the "Session applicative" (Application session) card proudly displays an `active`
session, a masked token `ops_....1f0d` and a source `cache local`. Everything looks in order.

## Step-by-step diagnosis

1. **Network**: the `solve` request does go out. Method `POST`, `Content-Type: application/json`,
   correct body. Status **403** (not 401: the header is there, it is its **value** that is refused).
2. **Headers** tab → *Request Headers*: `X-Api-Token: ops_7c1e4b0a9d2f6e8c3b5a1f0d`.
   **Response** tab: "is present but its value does not match the current session", with the last
   four characters of the token received and of the expected one: they differ.
3. Filter Network on `session`: **no** `GET /api/session` has been issued since the page loaded.
   So where does this token come from?
4. The Session card says "source : cache local" and "émis le 12 août 2026" (issued on 12 August
   2026). **Application** tab → *Storage* → **Local Storage** → the dojo's origin → key
   `pricing.session`:
   ```json
   {"provider":"sso-corp","token":"ops_7c1e4b0a9d2f6e8c3b5a1f0d",
    "issuedAt":"2026-08-12T07:41:09Z","expiresAt":"2027-08-12T07:41:09Z",...}
   ```
   The token ends in `1f0d`, like the masked display. That is where it comes from.
5. Compare with the real session, in the **Console**:
   ```js
   await (await fetch('/api/session')).json()
   ```
   The returned `token` is different, and its last four characters are the ones the 403 response
   announced as expected. The cache is stale relative to the current session, but not according to
   its own expiry date.
6. **Sources** → `16.js`: `cached()` only tests `expiresAt`, `getSession()` only calls
   `/api/session` again if `cached()` returns `null`, and `seedFromHandoff()` filled the cache
   from the `<script id="sso-handoff">` block.

## Workarounds

**A. Purge the key from the Application tab (the cleanest)**
Application → Local Storage → right-click `pricing.session` → **Delete**. Then click
"Valider la commande" (Submit) directly, **without reloading**: `cached()` returns `null`,
`getSession()` calls `/api/session`, stores the fresh token and the send goes out with the right
value → **200**.
Why without reloading? Because on load `seedFromHandoff()` only copies the handoff
if the storage is empty, and after your deletion, it is. Deleting and then reloading
therefore takes you right back to square one (the log shows "session
restaurée depuis le handoff SSO" (session restored from the SSO handoff) again). If you have
already reloaded, delete the key once more and click.

**B. The same thing from the Console**
```js
localStorage.removeItem('pricing.session');
document.getElementById('publish-grid').click();
```
The click triggers `getSession()`, which no longer finds a cache and negotiates a fresh session
before sending. The Session card is not refreshed (it only is on load),
but the log shows "réponse 200" (response 200).

**C. Expire the cache instead of deleting it**
Application → Local Storage → double-click the value of `pricing.session` → replace
`"expiresAt":"2027-08-12T07:41:09Z"` with a past date, for example `"expiresAt":"2020-01-01T00:00:00Z"`,
confirm with Enter, then **reload**. This time reloading is the right idea: the storage
is not empty, so the handoff is not copied again; `cached()` returns `null`, and
`getSession()` replaces the expired entry with a fresh session. The Session card shows
"session fraîche" (fresh session) and the button works.

**D. Replay the request from the Console with the fresh token**
```js
const { token } = await (await fetch('/api/session')).json();
await fetch('/api/challenge/16/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'X-Api-Token': token },
  body: JSON.stringify({ challengeId: '16', action: 'validate' })
}).then(r => r.json());
```

**After resetting the challenge**: the dashboard's "reset" button purges the
`pricing.session` key. If you reset the challenge some other way (or switch browsers),
purge the key by hand. A cache whose validity depends only on a date written by the client
never resynchronizes with the current session: that is exactly why a cache that "never expires"
always ends up lying.

## The reflex to keep

- **401** = the secret is **missing**. **403** = the secret is **present but refused**.
  A 403 on a well-formed request says: "you have a value, but not the right one".
- When the page has a token **without having made any authentication request**, it comes
  from storage: `localStorage`, `sessionStorage`, a cookie, IndexedDB. The
  **Application** tab is the first place to open.
- A "cache first" logic whose validity depends only on a date written by the
  client never resynchronizes with the server. Comparing the cached value with the fresh
  value (`await (await fetch('/api/session')).json()`) settles it in ten seconds.
