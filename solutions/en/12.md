# Challenge 12: Opening the vault

**Difficulty:** ★★★ · **Family:** the request goes out, but it's not the right one.
The code lives in `public/c/12.js`, minified on a single line.

## Cause

On load, the page negotiates a session and **receives a token**:

```js
function ses() {
  return fetch("/api/session", { headers: { "Accept": "application/json" } })
    .then(function (r) { return r.json(); })
    .then(function (d) {
      K.t = d.token;              // <- the token is stored here
      K.ttl = d.expiresIn;
      K.scopes = d.scopes || [];
      E.sess.textContent = "ops-console / jeton " + mask(K.t);   // <- displayed masked
      ...
    });
}
```

`mask()` only shows the first 4 and the last 4 characters: the "Session" card
shows `ops_....36de`. The full token lives in `K.t`, inside a closure.

The send, however, never reuses it:

```js
fetch("/api/challenge/12/solve", {
  method: "POST",
  headers: { "Content-Type": "application/json", "Accept": "application/json" },
  body: JSON.stringify({ challengeId: "12", action: "validate", path: S.path, ... })
})
```

Correct verb, correct `Content-Type`, correct body. What is missing is the
`X-Api-Token` header the endpoint requires. The server answers **401**:
`Header "X-Api-Token" missing from the received request.`

Unlike most challenges, **the Goal box does not mention this requirement**:
it is the server's response that tells you about it. That is the real-world case: a protected
endpoint whose documentation is incomplete.

## Step-by-step diagnosis

1. **Network**: the request goes out, `POST`, `Content-Type: application/json`, valid body.
   Status **401**.
2. **Response** tab: `Header "X-Api-Token" missing from the received request.`
   The server named the missing header. What remains is finding the value.
3. **Do not filter Network on `solve`.** Scroll back up the full list of the page's requests:
   there is a `GET /api/session` issued on load, well before your click.
   Open it → **Response** tab:
   ```json
   { "ok": true, "session": "ops-console", "issuedAt": "...", "expiresIn": 3600,
     "scopes": ["vault:read","vault:unlock","pricing:publish","challenge:solve"],
     "token": "ops_xxxxxxxxxxxxxxxxxxxxxxxx" }
   ```
   The full token is right there. (The "renouveler" (renew) button on the Session card replays
   this call if you missed the first request.)
4. Cross-check in the UI: the Session card shows `ops_....36de`: the last 4 characters
   do match those in the response. You have the right value.
5. Another route, through the debugger: **Sources** → `12.js` → **Pretty print `{}`** →
   breakpoint in `ses()` on the line `K.t = d.token`. Reload, the pause hits, hover over `d`:
   the token is in the object. Or, on a breakpoint set inside `tx()`, simply evaluate `K.t`.
6. Last route, the most direct: in the Console,
   `await (await fetch('/api/session')).json()`: the endpoint is open.

## Workarounds

**A. Replay with the header (Console): fetch the token dynamically**
```js
const { token } = await (await fetch('/api/session')).json();
await fetch('/api/challenge/12/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'X-Api-Token': token },
  body: JSON.stringify({ challengeId: '12', action: 'validate' })
}).then(r => r.json());
```

**B. Copy as fetch + one header**
Network → right-click the `solve` request → *Copy as fetch*. Paste it in the Console, add
`'X-Api-Token': '<colle ici le token lu dans la reponse de /api/session>'` (paste the token read
from the `/api/session` response) inside `headers`, run it. A single line changes; everything
else in the original payload is preserved.

**C. Inject the header into all of the page's requests**
```js
const orig = window.fetch;
const { token } = await (await fetch('/api/session')).json();
window.fetch = (u, i = {}) => orig(u, String(u).includes('/solve')
  ? { ...i, headers: { ...(i.headers || {}), 'X-Api-Token': token } } : i);
document.getElementById('unlock-vault').click();
```
This is the version closest to the real fix: the page's button then works
normally, with its real payload.

## The reflex to keep

A `401` / `403` on an otherwise impeccable request = **a secret is missing, not a format
fix**. And that secret is almost always already somewhere in the page:
- a response received earlier in the Network tab (`/session`, `/me`, `/config`, `/bootstrap`),
- a `data-*` attribute in the DOM,
- a JS variable reachable on a breakpoint,
- `localStorage` / `sessionStorage` (**Application** tab),
- a cookie.

Hence the reflex: **look at all of the page's requests, not just the one that fails.**
The authentication context is almost always set up on load.
