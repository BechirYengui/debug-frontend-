# Défi 17 : Export des écritures comptables

**Difficulté :** ★★★ · **Famille :** la requête part, mais elle ne convient pas.
Le code est dans `public/c/17.js` et `public/c/17-guard.js`, minifiés sur une ligne.

## Cause

Le script de la page est irréprochable. Au clic, `tx()` envoie :

```js
fetch("/api/challenge/17/solve", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ challengeId: "17", action: "validate", period: S.period, format: S.format, recipient: S.recipient })
})
.then(function (r) { return r.json().then(function (j) { return { s: r.status, j: j }; }); })
.then(function (x) {
  log("réponse " + x.s + " : " + (x.j.message || x.j.error));
  if (x.s === 202) { E.chip.className = "chip chip-warn"; E.chip.textContent = "en attente de revue"; }
})
```

Le problème est ailleurs : dans le `<head>` du fragment, **avant** ce script, un second
fichier est chargé sans `defer` :

```html
<link rel="stylesheet" href="/c/17.css">
<script src="/c/17-guard.js"></script>
```

`17-guard.js` (« garde-fou de confidentialité ») **remplace `window.fetch`** :

```js
(function (w) {
  var nf = w.fetch;                                   // <- le vrai fetch, gardé en closure
  var ALLOW = [/\/api\/session\b/, /\/api\/telemetry\b/, /\/_dojo\//];
  function held(u, i) {
    var m = ((i && i.method) || "GET").toUpperCase();
    if (m === "GET" || m === "HEAD") return false;    // les lectures passent
    if (!/\/api\//.test(u)) return false;
    for (var k = 0; k < ALLOW.length; k++) { if (ALLOW[k].test(u)) return false; }
    return true;                                      // tout POST /api/... non listé est retenu
  }
  function quarantine(u, i) {
    ...
    console.debug("[privacy-guard] requête retenue pour revue : POST " + u + " (q-1)");
    return Promise.resolve(new Response(body, { status: 202, headers: { "Content-Type": "application/json" } }));
  }
  w.fetch = function (u, i) {
    var s = str(u);
    if (held(s, i)) return quarantine(s, i);          // <- répond 202 SANS toucher au réseau
    return nf.apply(w, arguments);
  };
})(window);
```

`POST /api/challenge/17/solve` n'est pas dans la liste blanche : l'enveloppe fabrique une
`Response` **202** de toutes pièces et la renvoie. **Aucun octet ne part.** La page, de bonne
foi, journalise « réponse 202 : Requête mise en quarantaine… » et passe la chip en
« en attente de revue ». Le serveur, lui, n'a jamais rien reçu.

## Diagnostic pas à pas

1. **Les trois miroirs divergent.** Le journal de la page affirme « réponse 202 ».
   Le panneau « Dernière réponse du serveur » du dojo reste vide, le terminal du serveur
   n'affiche rien. Et surtout : dans **Network**, il n'y a **aucune requête `solve`**, même
   sans filtre, même en cochant *Preserve log*. Un 202 sans requête réseau, ça n'existe pas.
   Donc ce 202 n'est pas venu du réseau : quelqu'un l'a fabriqué dans la page.
2. **Console** → tape `fetch` et valide. Un `fetch` natif s'affiche `ƒ fetch() { [native code] }`.
   Ici tu obtiens `ƒ (u, i){var s=str(u);if(held(s,i)){return quarantine(s,i);}…}` :
   `window.fetch` a été **remplacé**. `fetch.toString()` donne le même verdict en clair.
3. Clique sur `ƒ (u, i)…` dans la Console : DevTools ouvre **Sources** sur la définition,
   dans `17-guard.js`. Clique sur **`{}`** (Pretty print). Tu vois `nf = w.fetch`, la liste
   `ALLOW`, `held()`, `quarantine()` et la `new Response(..., {status: 202})`.
4. Confirmation par le journal caché : dans la Console, règle le niveau sur **Verbose**
   (menu *Default levels* → coche *Verbose*), reclique sur le bouton : la ligne
   `[privacy-guard] requête retenue pour revue : POST /api/challenge/17/solve (q-2)` apparaît.
   Elle était là depuis le début, filtrée par le niveau par défaut.
5. Où est chargé ce script ? **Network** → filtre `JS` → `17-guard.js`, colonne **Initiator** :
   le document lui-même (`17`), c'est-à-dire une balise `<script>` du `<head>`, chargée avant
   `17.js`. **Elements** → `<head>` : la balise est visible.
6. Pour voir le vrai `fetch` : point d'arrêt dans l'enveloppe (Sources, `17-guard.js`
   pretty-printé, ligne `var s = str(u)`), clique sur le bouton, à la pause le panneau
   **Scope** → *Closure* montre `nf: ƒ fetch() { [native code] }`.

## Contournements

**A. Bloquer le script du garde-fou (le plus propre)**
Network → clic droit sur `17-guard.js` → **Block request URL** → recharge (`F5`).
Le script ne se charge plus, `window.fetch` reste natif, le clic sur « Valider la commande »
envoie la vraie requête → **200**. (Même résultat depuis Sources → onglet
*Network request blocking*.) N'oublie pas de débloquer après.

**B. Restaurer le fetch natif depuis la pause**
Pose un point d'arrêt dans l'enveloppe (`17-guard.js` pretty-printé, ligne `var s = str(u)`),
clique sur le bouton. À la pause, dans la Console : qui évalue dans le scope de la closure :
```js
window.fetch = nf
```
Puis `F8`. Cet appel-ci est encore intercepté (il était déjà entré dans l'enveloppe),
mais **le clic suivant** passe par le fetch natif → 200.

**C. Récupérer un fetch natif via un iframe (sans point d'arrêt)**
```js
const f = document.createElement('iframe');
document.body.appendChild(f);
window.fetch = f.contentWindow.fetch.bind(window);
document.getElementById('send-export').click();
```
Le `fetch` d'une fenêtre neuve n'a pas été enveloppé. Lié à `window`, il fait le travail
du fetch natif de la page ; le bouton fonctionne ensuite normalement.

**D. Contourner `fetch` avec `XMLHttpRequest` (Console)**
`XMLHttpRequest` n'est pas enveloppé. Requête complète :
```js
const x = new XMLHttpRequest();
x.open('POST', '/api/challenge/17/solve');
x.setRequestHeader('Content-Type', 'application/json');
x.onload = () => console.log(x.status, x.responseText);
x.send(JSON.stringify({ challengeId: '17', action: 'validate' }));
```

**E. Rejouer la requête depuis la Console, mais pas celle de cette page**
Le rejeu habituel :
```js
await fetch('/api/challenge/17/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '17', action: 'validate' })
}).then(r => r.json());
```
**échoue** si tu le tapes dans la Console de la page du défi : la Console utilise le `fetch`
de la page, donc l'enveloppe, et tu récupères un 202 fabriqué : le serveur ne voit toujours
rien. Exécute exactement le même code depuis la Console d'un **autre onglet** de la même
origine (le tableau de bord, par exemple, qui ne charge pas `17-guard.js`), ou depuis un
terminal :
```sh
curl -s -X POST http://localhost:3000/api/challenge/17/solve \
  -H 'Content-Type: application/json' \
  -d '{"challengeId":"17","action":"validate"}'
```
(adapte le port à celui affiché au démarrage du serveur). Le défi passe : la validation est
côté serveur, peu importe l'onglet d'où part la requête.

## Le réflexe à garder

Quand **le journal de l'application et l'onglet Network se contredisent, c'est la page qui
ment**, jamais Network : DevTools observe la couche réseau du navigateur, en dessous de tout
ce que du JavaScript peut réécrire. Un « succès » sans ligne dans Network est un succès
fabriqué. Premier geste : `fetch` dans la Console : si tu ne lis pas `[native code]`, un
script tiers (analytics, « privacy guard », SDK d'erreur, polyfill) s'est intercalé, et la
Console ne te sert plus à rejouer quoi que ce soit tant que tu ne l'as pas neutralisé.
Deuxième geste : niveau **Verbose**, où ces scripts déposent souvent leurs aveux.
