# Défi 15 : Signature d'un bon de commande

**Difficulté :** ★★☆ · **Famille :** la requête part, mais elle ne convient pas.

## Cause

Le code construit lui-même l'adresse de l'API, et il choisit une **autre origine** que celle
de la page. En tête de `public/c/15.js` (lignes 4-9) :

```js
var GATEWAY = {
  primary: location.origin,
  replica: location.protocol + '//' + location.hostname + ':' +
    (parseInt(location.port || (location.protocol === 'https:' ? '443' : '80'), 10) + 1),
  prefer: 'replica'                                   // <- le « réplica » est préféré
};
```

puis (lignes 31-33 et 96) :

```js
function apiBase() {
  return GATEWAY.prefer === 'replica' ? GATEWAY.replica : GATEWAY.primary;
}
...
fetch(apiBase() + '/api/challenge/15/solve', { method: 'POST', ... })
```

Si la page est servie sur `http://localhost:3000`, `GATEWAY.replica` vaut
`http://localhost:3001` : même schéma, même hôte, **port différent**, donc une origine
différente. Le serveur écoute bien sur ce port voisin, avec la même application, mais sans
aucun en-tête CORS.

Un `POST` avec `Content-Type: application/json` vers une autre origine n'est pas une
« requête simple » : le navigateur envoie d'abord un **preflight** `OPTIONS` pour demander
la permission. Le serveur répond `405` sans `Access-Control-Allow-Origin` ; le navigateur en
conclut que l'origine `http://localhost:3000` n'est pas autorisée, **bloque** et n'émet
jamais le `POST`. Le `fetch` est rejeté avec `TypeError: Failed to fetch`, que le journal
de la page affiche honnêtement : « échec réseau : Failed to fetch ». Verbe, en-tête,
corps : tout est correct : c'est l'**adresse** qui ne va pas.

## Diagnostic pas à pas

1. **Console**, clic sur *Valider la commande* : un message rouge, long, qu'il faut lire en
   entier :
   `Access to fetch at 'http://localhost:3001/api/challenge/15/solve' from origin
   'http://localhost:3000' has been blocked by CORS policy: Response to preflight request
   doesn't pass access control check: No 'Access-Control-Allow-Origin' header is present on
   the requested resource.`
   Il contient déjà tout : l'URL cible (port **3001**), l'origine de la page (port
   **3000**), le mot *preflight* et l'en-tête manquant.
2. **Network** : la ligne `solve` est en rouge, colonne Status : **CORS error**. Vérifie le
   filtre en haut du panneau : sur *Fetch/XHR*, tu ne vois que la requête bloquée ; passe sur
   *All* (ou *Other*) pour voir apparaître la **seconde** ligne `solve`, colonne Type
   `preflight`, méthode `OPTIONS`, statut 405. Ouvre-la → **Headers** : la requête porte
   `Origin: http://localhost:3000` et `Access-Control-Request-Method: POST` ; la réponse n'a
   aucun en-tête `Access-Control-*`.
3. **Terminal du serveur** (`npm start`) : il a bien reçu quelque chose : un
   `OPTIONS /api/challenge/15/solve` avec l'en-tête `origin`, et rien d'autre. Tu n'as écrit
   aucun `OPTIONS` : c'est le navigateur qui l'a émis à ta place. Le `POST`, lui, n'est
   jamais arrivé.
4. **Sources** → `15.js` → `Ctrl+F` `fetch` : l'URL est `apiBase() + '/api/...'`. Remonte à
   `apiBase()`, puis à `GATEWAY` : `prefer: 'replica'` et le calcul `location.port + 1`.
   Le journal de la page le disait dès le chargement : « passerelle sélectionnée : réplica ».
5. Confirme l'origine attendue : dans la Console, `location.origin` →
   `"http://localhost:3000"`. C'est vers **ça** que la requête doit partir.

## Contournements

**A. Rejouer la requête depuis la Console, en URL relative**
Une URL relative est résolue sur l'origine de la page : plus de CORS, plus de preflight.
```js
await fetch('/api/challenge/15/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '15', action: 'validate' })
}).then(r => r.json());
```

**B. Basculer la passerelle pendant une pause du débogueur**
Point d'arrêt sur la ligne 96 (`fetch(apiBase() + ...)`) dans `sign()`, clic sur le bouton.
En pause, `GATEWAY` est dans le scope de la closure :
```js
GATEWAY.prefer = 'primary'
```
`F8` : `apiBase()` renvoie désormais `location.origin`, le `POST` part sur la bonne origine,
le journal affiche « réponse 200 ». Retire le point d'arrêt ; le réglage tient pour toute la
session.

**C. Partir de la requête bloquée (Network → Copy as fetch)**
Clic droit sur la ligne `solve` (celle en *CORS error*) → **Copy** → *Copy as fetch*. Colle
dans la Console, et remplace `"http://localhost:3001/api/challenge/15/solve"` par
`"/api/challenge/15/solve"`. Tout le reste (méthode, en-têtes, corps) est déjà bon :
tu montres exactement ce que tu changes, et rien d'autre.

**D. Corriger le fichier servi (Sources → Overrides)**
**Sources** → onglet *Overrides* → *Select folder for overrides*, autorise l'accès. Ouvre
`15.js`, remplace `prefer: 'replica'` par `prefer: 'primary'`, `Ctrl+S`. Le fichier est
désormais servi depuis ton disque, même après rechargement : c'est la manière propre de
tester un correctif front sans redéployer.

## Le réflexe à garder

Une origine, c'est **schéma + hôte + port**, les trois ensemble : `localhost:3000` et
`localhost:3001` sont deux origines étrangères l'une à l'autre. Un `OPTIONS` que tu n'as
pas écrit dans ton code est un **preflight** : le navigateur demande la permission avant
d'envoyer ta vraie requête, et si la réponse ne l'accorde pas, cette vraie requête n'existe
jamais (ni dans Network au sens strict, ni côté serveur). Devant « blocked by CORS policy »,
lis le message jusqu'au bout : il nomme l'origine et la cible, puis pose la seule question
utile : *pourquoi le client vise-t-il une autre origine ?* La correction côté client est
presque toujours la même : **une URL relative, donc la même origine.**
