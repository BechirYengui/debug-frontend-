# Défi 09 : Mise à jour de firmware

**Difficulté :** ★★☆ · **Famille :** la requête part, mais elle est invalide.

## Cause

La page passe par un mini-client HTTP maison :

```js
var api = {
  request: function (url, opts) {
    opts = opts || {};
    var method = (opts.method || 'GET').toUpperCase();   // <- defaut GET
    var init = { method: method, headers: {} };
    ...
    if (opts.json !== undefined && method !== 'GET' && method !== 'HEAD') {
      init.headers['Content-Type'] = 'application/json';
      init.body = JSON.stringify(opts.json);
    }
    return fetch(url, init) ...
  }
};
```

et l'appelant oublie de préciser le verbe :

```js
api.request('/api/challenge/09/solve', {
  headers: { Accept: 'application/json' },
  json: { challengeId: '09', action: 'validate', ... }   // <- pas de `method`
});
```

Le helper retombe sur son défaut `GET`. Et comme un `GET` ne peut pas porter de corps
(`fetch` lèverait `TypeError: Request with GET/HEAD method cannot have body`), le helper
prend soin de **ne pas attacher le body ni le Content-Type** dans ce cas. La requête part donc
en `GET`, sans corps, sans type de média : le serveur répond `405` et le journal du terminal
affiche `body brut : (vide)`.

Le piège : le helper est correct, l'appelant est incomplet, et le défaut choisi masque l'oubli
au lieu de le signaler.

## Diagnostic pas à pas

1. **Network** : au clic, une ligne `solve` apparaît : c'est déjà une bonne nouvelle,
   la requête part. Elle est en rouge, statut **405**.
2. Colonne **Method** : `GET`. L'encart Objectif exige `POST`. Diagnostic terminé.
   (Si la colonne Method n'est pas affichée : clic droit sur l'en-tête du tableau → coche *Method*.)
3. Ouvre la requête → **Headers** :
   - *Request Method: GET*
   - pas de `Content-Type`
   - onglet **Payload** absent : il n'y a pas de corps.
4. Onglet **Response** : le serveur dit exactement ce qu'il a reçu :
   `Verbe recu : GET. Cet endpoint ne traite pas ce verbe.`
5. Le terminal `npm start` confirme la même chose côté serveur.
6. **Sources** → `09.js` → cherche `fetch`. Tu remontes à `api.request` et à son
   `opts.method || 'GET'`, puis à l'appel qui ne passe pas de `method`.

## Contournements

**A. Rejouer la requête correctement (Console)**
```js
await fetch('/api/challenge/09/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ challengeId: '09', action: 'validate' })
}).then(r => r.json());
```

**B. Partir de la requête existante (Network)**
Clic droit sur la ligne `solve` → **Copy** → *Copy as fetch*. Colle dans la Console et corrige
les trois points : `method: 'POST'`, ajout de `Content-Type`, ajout du `body`. C'est le geste
le plus rapide en entretien : tu pars de ce qui existe, tu montres exactement ce que tu changes.

**C. Corriger le helper à chaud (Console)**
Le helper est dans une closure, mais tu peux intercepter en amont :
```js
const orig = window.fetch;
window.fetch = (url, init = {}) => {
  if (String(url).includes('/solve')) {
    init = { ...init, method: 'POST',
             headers: { ...(init.headers || {}), 'Content-Type': 'application/json' },
             body: JSON.stringify({ challengeId: '09', action: 'validate' }) };
  }
  return orig(url, init);
};
document.getElementById('push-firmware').click();
```

## Le réflexe à garder

Dès que la requête **part**, le débat se déplace : ce n'est plus « pourquoi rien ne se passe »
mais « qu'est-ce que j'envoie exactement ». Network → Method, Status, Headers, Payload, dans
cet ordre. Un helper HTTP avec un verbe par défaut est un nid à bugs : le code compile, part,
et échoue seulement côté serveur. *Copy as fetch* est ton meilleur point de départ pour
rejouer et corriger.
